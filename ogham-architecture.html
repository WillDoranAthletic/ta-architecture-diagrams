AWSMA isn't one network
DVSP shared-EKS VPC (Lettercase) and AWSMA-account VPCs (MSK, S3 Interface VPC Endpoint) are distinct VPCs themselves peered via dv-awsma-vpc-routes. Pattern Y is technically Lettercase-VPC -> AWSMA-account-VPC -> cross-account peering -> TA-VPC, two peering hops if you count the internal NYT one. Same-account does not imply same-network.
Symmetric repo placement
AWSMA-side resource policies, IRSA roles, peering accepters, and VPC endpoints live in nytimes/dv-awsma-accounts-theathletic-{dev,prd}. TA-side identity policies, peering requesters, and the OpenSearch domain access policy live in theathletic-iac-envs. Cache Purge Lambda role hoisted from theathletic-serverless into theathletic-iac-envs so all TA-side cross-account-touching role definitions sit alongside their grants.
CC-2018 + CC-3178 dependency chain
CC-2018 (DONE 2026-04-06) established bidirectional TA <-> AWSMA peering, validated all 11 scenarios including S8 (TA Lambda -> AWSMA MSK p50 1417ms consume). CC-3178 (Fernanda, in-flight) flips the dev peering ACTIVE for Data Skrive's TA -> AWSMA producer; same primitives, opposite direction. Cache Purge piggybacks on (a) peering, (b) cluster-policy entry, (c) route-table extension. Most of the "6-8 IaC steps x 3 envs" in ADR v3 is already plumbed waiting to be activated.

1. Two source/renderer pipelines — parallel, disjoint ID namespaces

WordPress renders WP-authored articles (integer IDs) forever. Stride renders Pitch-authored articles (Scoop UUIDs) forever. An article belongs to exactly one pipeline for life.

2. New push-adapter services (fan-out from Storytelling MSK)

Five services subscribe to the Stride MSK topic to ship Pitch-authored articles to downstream destinations. Four are new DVSP services (OpenSearch Indexer, Alice Shipper, PubP Shipper, Push Shipper); Cache Purge extends an existing Lambda.

3. Existing WordPress pipeline — continues in parallel (WP-authored articles only)

Every destination below keeps receiving WP-authored articles via the existing WP code paths. Stride does not replay these; the same destinations receive Stride articles via section 2.

4. Apollo unified reads and pull surfaces

Apollo is the unifying reader. Body-fetch routing by ID shape is BUILT on feature branches (CC-1845 PR #7526 on theathletic-apollo-express, awaiting merge from cc-1560 / cc-1560-1 / jl/cc-1846-sitemap): integer → athleticRestDataSource → WP REST → wpdb; UUID → s3ArticleDataSource → ta-rendered-articles S3 via Cognito Identity Pool. Apollo sprinkles ads (sprinkleDropzonesDesktop/Mobile) and ICMs (sprinkleInContentModules via graphicsDataSource) + dark-mode theme on read for BOTH paths; Stride's S3 output is pre-sprinkle HTML. Remaining Apollo work: add the Scoop data source alongside the WP data source for list resolvers (Pattern C merge), plus reworking Iterable off direct MySQL.

5. Analytics Event Bus coexistence

The Confluent TA Analytics Event Bus and the new Storytelling MSK are separate clusters. Confluent is Data Platform owned and carries ~13 non-article topics. Stride MSK is TA-owned and carries article render events only.

6. Deferred / out-of-scope

Not part of the Stride integration. Shown dimmed for completeness.
